## The branch predictor bug that profiling found (great interview story)

**Symptom.** The first study showed a **27.8% mispredict rate** with gshare enabled, far too high. A bigger BTB and BHT barely helped (309k → 278k mispredicts). That says *structural problem*, not capacity.

**Diagnosis.**
- A debug build (`+define+BP_DEBUG`) logged every mispredict with its PC and type.
- 87% were **taken conditional branches predicted not-taken**.
- All of the top offenders were **32-bit branches at halfword offset 2**: instructions that straddle two fetch words.

**Root cause.**
- My original design never installed straddling branches in the BTB, because the BTB is indexed by fetch-word address and the aligner couldn't attach a prediction to an instruction spanning two words.
- With compressed code about half of all 32-bit instructions start at offset 2, so roughly half of all branches were invisible to the predictor.

**Fix.**
- Install a straddling branch under the word where it *ends*, with an `xe` ("ends here") flag.
- When the aligner assembles a straddling instruction, it takes the prediction from the second word, then drops both words.
- The stale-entry repair logic got one more case: an `xe` prediction reaching the head without its owner.

**Result.**

| | Before | After |
|---|---|---|
| Mispredicts | 309k | 114k |
| Mispredict rate | 27.8% | 10.3% |
| CoreMark IPC | 0.725 | 0.808 (**+11%**) |

**Verification of the fix.**
- The full regression passes, and a new directed test (`sw/tests/bp_fixup.S`) uses self-modifying code to create stale `xe` entries.
- Code coverage confirmed the repair path is now exercised.

## Where the remaining cycles go (CoreMark, baseline)
- **Mispredicts**: 114k × 4-cycle penalty ≈ 460k cycles ≈ 7% of runtime.
- **I-cache misses**: 24k × ~9 cycles ≈ 220k cycles. A 16 KiB I-cache removes these.
- **Load-use stalls, MUL (2-cycle), DIV (~33 cycles)**: the rest of the gap to IPC 1.
- Ideas, in order of value:
  1. Bigger I-cache.
  2. A resolve-in-ID path for `jal` (no EX wait).
  3. A next-line I-prefetcher.
  4. A faster radix-4 divider.

## Interview Q&A
- **How do you measure IPC in hardware?** `mcycle`/`minstret` CSRs, plus the `mhpmcounter3-8` performance counters this core implements:
  - mispredicts, control-flow instructions;
  - load-use stall cycles, front-end-starved cycles;
  - D-bus stall cycles, divider stall cycles.
- **Why CoreMark over Dhrystone?** Dhrystone is dominated by string copies and is easy for compilers to game. CoreMark mixes list processing, matrix math and state machines, and self-checks its results with CRCs.
- **Why is Dhrystone IPC lower than CoreMark's?** `-fno-inline` makes it call-heavy (returns, RAS) with many short loops. Its I-cache footprint also differs.
